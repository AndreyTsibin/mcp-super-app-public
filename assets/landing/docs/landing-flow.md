# Генератор сайтов — флоу

Ты собираешь сайт под ключ: пользователь описывает, какой нужен — ты выдаёшь готовую
**сборку для хостинга** (`dist/` + `send.php`). Пользователь может быть неопытным,
запрос — короткий и неточный, это норма. Структуру, тексты, тему и картинки готовишь
сам; у пользователя спрашиваешь только то, что нельзя угадать, плюс он выбирает тему
из твоих вариантов.

Детальные стандарты лежат в `docs/` — на каждом шаге флоу указано, какой файл прочитать.
Читай его в этот момент, не держи всё в голове заранее.

## Одна сессия = один шаг

Этот файл — карта всего пути, а **не программа одной сессии**. Порядок работы
держит `docs/_dev/tracker.md`: каждая строка там = один шаг отсюда = одна сессия.
Взял первую незакрытую задачу → сделал → билд зелёный → проверил в превью → коммит →
отметил в трекере → переписал `.claude/HANDOFF.md` → **стоп**.

Пройти все восемь шагов за один заход нельзя, даже если контекст ещё позволяет:
без коммитов по дороге откатывать неудачный ход некуда, а качество текстов и вёрстки
падает задолго до конца контекста. Правило записано в `.claude/CLAUDE.md`.

Соответствие шагов задачам трекера (на номера шагов ссылаются стандарты, поэтому
нумерация здесь своя):

| Шаг флоу | Задача трекера |
|---|---|
| 1–2 — бриф, профиль ниши, карта страниц, набор секций | 1 |
| 3 — тема | 2 |
| 4 — контент: тексты в data-файле | 3 |
| 4 — сборка страниц из секций | 4 |
| 5 — картинки | 5 |
| 6 — заявки и домен | 6 |
| 7 — критика-луп | 7 |
| 8 — приёмка и упаковка | 8 |

Один проект = один сайт. Это может быть одностраничный лендинг или многостраничник —
на Astro каждый файл в `src/pages/` становится маршрутом, так что второй случай ничем
не сложнее первого.

## Главный принцип — собираешь из библиотеки, а не верстаешь с нуля

В проекте уже лежит **библиотека из 21 секции** (`src/components/`), тема на токенах
и рабочие страницы-образцы. Твоя работа — выбрать секции под нишу, наполнить их
контентом и подобрать тему. Верстать разметку заново не нужно и не надо.

Уникальность даёт не своя сетка, а **тема + контент + композиция**: набор и порядок
секций, вариант каждой секции (`variant`), палитра, шрифты, тексты и картинки под
конкретную компанию. Одна и та же библиотека под стоматологию и под эвакуатор даёт
два непохожих сайта.

**Потолок не занижен.** Библиотека — быстрый старт, а не запрет. Если ниша требует
секции, которой нет, или существующая не ложится — правь компонент или добавь свой
по образцу соседей (`docs/tech-standard.md` → «Как добавить секцию»). Единственное
жёсткое ограничение: **секции читают только токены** из `src/styles/tokens.css`,
хардкод-цветов и своих шрифтов в компонентах быть не должно — иначе смена темы ломает
вёрстку. И контракт заявок (`docs/ЗАЯВКИ-инструкция-для-Claude.md`) не трогаем никогда.

## Шаблон даёт сетку, а не контент

В библиотеке нет ни одной готовой ниши — только сетка. Все тексты в `placeholder.ts`
и в каркасах страниц записаны маркерами `[[…]]`, где сказано, что писать и какой
длины; картинки — серые SVG-заглушки. Это сделано намеренно: **копировать нечего,
каждую строку пишешь ты**. Оставшийся в сборке маркер `[[…]]` или заглушка
`placeholder-*.svg` роняют валидатор с ошибкой — «доделаю потом» не проходит.

Секции тоже ничего не досочиняют за тебя: не передал `eyebrow`, `note`, `badgeLabel` —
элемента на странице просто нет. Никакой чужой текст не подставится молча.

## Перед началом

Скиллы `/ui-ux-pro-max`, `/frontend-design`, `/humanizer-ru` и `/image` уже поставлены
в проект (их ставит `scaffold_landing`) — используй их по флоу. Если скиллов нет
в доступных — сессия была запущена до их установки: остановись и попроси пользователя
перезапустить приложение/сессию Claude Code (скиллы подхватываются только на старте).

Зависимости Astro ставит `scaffold_landing`. Если `npm run dev` не стартует — сначала
`npm install`.

## Флоу

1. **Понять запрос и собрать бриф.** Определи нишу и ЦА из фразы пользователя. Спроси
   недостающий минимум коротко и просто, **одним блоком** — см. «Что уточнить». Не гоняй
   термины и развилки по дизайну/коду на пользователя — тему он выберет на шаге 3
   из готовых вариантов.

2. **Профиль ниши, карта сайта и набор секций** — по `docs/landing-spec.md` (прочитай
   сейчас). Определи профиль (**urgency** — «горит, звонит первому» / **trust** —
   «выбирает, кому довериться»), от него — первый экран, тип CTA и набор секций из
   каталога. Реши, одна страница или несколько (см. «Когда нужен многостраничник»).
   Зафиксируй план: список страниц, на каждой — секции по порядку с вариантами.
   Полигон всех секций и вариантов — страница `/kit` в превью.

3. **Тема** — по `docs/design-standard.md` (прочитай сейчас). Перепиши
   `src/data/themes.ts`: три контрастные темы под нишу (палитра + шрифтовая пара) →
   покажи `/themes` в превью → **пользователь выбирает** (СТОП-точка; можно миксовать) →
   перенеси токены выбранной темы в `src/styles/theme.css` и её шрифты в `fontsHref`
   BaseLayout. Дальше вёрстка и картинки подчиняются теме.

4. **Контент и сборка страниц.** Заведи `src/data/<проект>.ts` по структуре
   `src/data/placeholder.ts` (сам placeholder НЕ редактируй — на нём держатся `/kit`
   и `/themes`) и собери страницы из секций по плану шага 2. `src/pages/index.astro`
   и `src/pages/uslugi/primer-stranicy.astro` — каркасы из обязательного минимума
   секций: переключи импорт на свой data-файл, добери тело страницы по плану шага 2,
   внутреннюю страницу переименуй под свой маршрут или удали. Тексты — по
   `docs/landing-spec.md` → «Копирайтинг»: скелет Hook–Problem–Solution–Proof–Action,
   язык уровня 5–7 класса, заголовки = выгода, CTA конкретные. Финальный проход —
   `/humanizer-ru` (канцелярит, «является», кальки, тире-связка) как чек-лист
   редактуры: смысл, числа, имена и термины не трогай. Именно `/humanizer-ru`:
   одноимённый глобальный `/humanizer` заточен под английский и на русском правит не то.
   Технику сборки (маршруты, canonical, навигация, пропсы) — `docs/tech-standard.md`.

5. **Картинки** — по `docs/image-standard.md` (прочитай сейчас). Кратко: hero + 2–4
   поддерживающих; промпты скиллом `/image` со стилем выбранной темы в каждом; hero
   генерируется первым и идёт в `reference_images` остальных (одна «фотосессия»);
   кладутся в `src/assets/img/`, в конце — один вызов `optimize_images` на эту
   папку. В data-файл подставь ИМПОРТЫ картинок, не строки — на импортах Astro
   строит `srcset`.

6. **Заявки и домен.** Заявки — строго по `docs/ЗАЯВКИ-инструкция-для-Claude.md`
   (форма → `public/send.php` → вебхук CRM). Заготовки уже в проекте — подставь
   `WEBHOOK_URL` и ссылку на политику. Контракт полей не меняй, см. «Заявки — жёсткие
   правила». Тут же пропиши боевой домен в `astro.config.mjs` (`site`) — из него
   собираются canonical и абсолютные OG-ссылки; останется `example.com` — поисковик
   получит чужой канонический адрес.

7. **Критика-луп** — по `docs/critique-standard.md` (прочитай сейчас). Превью на
   375 / 768 / 1440 (скриншоты — нативными браузер-тулами), рубрика с баллами,
   quality gate: все оси ≥ 7 и средняя ≥ 8. **Максимум 2 итерации правок** — дальше плато.

8. **Финальная проверка и упаковка.** Собери прод-сборку и прогони валидатор:
   ```
   npm run build && node .claude/check-landing.mjs
   ```
   ❌-ошибки чини обязательно и перезапускай до чистого прогона; ⚠️-предупреждения —
   осознанное решение (пиши в отчёте, почему оставил). Валидатор не заменяет живую
   проверку формы — Шаг 7 инструкции заявок выполни отдельно.

   Затем упаковка в zip и отчёт — см. ниже.

## Что уточнить у пользователя (минимум, простым языком)

Обязательно (без этого сайт не сделать): **город, телефон, название компании / имя
мастера, домен** (домен нужен для canonical и OG — нет домена, так и скажи в отчёте).

По возможности (нет — действуй по дефолту, генерацию НЕ блокируй):
- **Полный URL вебхука CRM** — нет → плейсхолдер `URL_ВЕБХУКА_ОТ_ЧЕЛОВЕКА` в send.php + пометка
  в отчёте.
- **Ссылка на политику конфиденциальности** — нет → в проекте уже есть страница
  `/privacy` (типовая под 152-ФЗ), подставь в неё реквизиты из брифа.
- **Коллтрекинг (Колокол)** — по умолчанию нет; да → проси loader-сниппет.
- **Реальные фото** (мастер/команда, работы, объект) — сильно лучше генерации, особенно
  для trust-ниш; нет → картинки генеришь сам (шаг 5), но людей и «работы» не подделывай.
- **Тексты / отзывы** — нет → тексты пишешь сам, отзывы — реалистичный placeholder.
  Выдуманные цифры (цены, опыт, акции) ставь реалистичными и помечай в отчёте как
  «проверь / замени» — чтобы ничего не ушло в прод молча.

Полный шаблон ТЗ (для структурированного брифа) — `docs/TEMPLATE_tz.md`.

## Выход

`npm run build` собирает сайт в `dist/` — это и есть то, что уезжает на хостинг:
готовый HTML всех страниц, CSS/JS в `_astro/`, картинки и `send.php` (всё из `public/`
копируется как есть). Исходники (`src/`, `docs/`, `node_modules/`) на хостинг не идут.

## Заявки — жёсткие правила (нарушение ломает заявки молча)

- Контракт полей не менять: `Phone`/`Name`/`Message` — заглавные; `form_id`/`page_url`/
  `ip`/`origin`/`kolokol_token` — lowercase.
- Honeypot (`website`) и согласие (`consent`) — обязательны.
- URL вебхука не придумывать и не достраивать — брать у пользователя целиком и вставлять как есть.
- `lead-form.js` подключается с `?v=` (уже так в BaseLayout). Реальный `WEBHOOK_URL` —
  только в `public/send.php`, не в публичный git.
- `lead-form.js` цепляется за `name` и `data-*`, а не за классы — CSS формы темизируй
  свободно, разметку не трогай.

Полный пошаговый стандарт (код send.php, lead-form.js, разметка формы) —
`docs/ЗАЯВКИ-инструкция-для-Claude.md`.

## Упаковка и отчёт

Упаковка (из корня проекта; архив кладётся уровнем выше — только прод-сборка):
```
npm run build && (cd dist && zip -r "../../<название>.zip" . -x "*.DS_Store")
```

Отчёт:
```

🎨 Тема: [название] — палитра #XXXXXX / #XXXXXX / #XXXXXX, шрифты [заголовки + текст]
```
