# 🛠 INSTALL — установщик нового проекта (читает Claude Code, не человек)

> **Это исполняемая инструкция для агента, а не методичка для чтения.**
> Когда пользователь говорит «прочти INSTALL.md и разверни проект» (или просто
> «разверни проект») — выполняй шаги ниже по порядку, сверху вниз.
> Методология, на которой всё построено, лежит в [PROJECT-BOOTSTRAP.md](PROJECT-BOOTSTRAP.md) —
> сверяйся с ней, если нужен контекст «почему так».
>
> **Принцип:** ты — установщик. Спроси минимум, разверни каркас, убери за собой,
> отдай пользователю чистый готовый к работе проект.

---

## Шаг 0 — Собрать бриф (обязательно, до создания файлов)

Не угадывай. Спроси у пользователя коротко (одним блоком вопросов):

1. **Название проекта** (для заголовков и памяти).
2. **Что строим** — 1–2 предложения: что это и для кого. Пойдёт в product-vision.
3. **Стек** — свободным текстом, что есть: «статичный лендинг HTML/CSS/JS», «React SPA»,
   «Next.js fullstack», «Python API», «мобилка» и т.д. Или «реши сам / пока не знаю».
   Нужно для `.gitignore` и `.claude/settings.json`.
4. **Профиль проекта** — управляет глубиной каркаса (см. ниже). Если не назван — выведи
   сам из п.2–3 и подтверди одной строкой.

`work-protocol` и cold-start (Шаг 5) ставятся **всегда**, для любого профиля — это ядро метода,
не опция. Спрашивать тут нечего.

### Профили (масштаб → глубина каркаса)

Ключевой принцип универсальности: **не вываливать структуру крупного продукта на простой
лендинг**. Чем проще проект — тем тоньше каркас. Детально документируем только то, что есть
сейчас; остальное — крупными мазками или вовсе не создаём.

| Профиль | Что это | Каркас `docs/` (Шаг 3) |
|---------|---------|------------------------|
| **S — простой** | Статичный лендинг/одностраничник, скрипт, прототип | Минимальный: `docs/` плоско (один `README.md`) или `docs/_dev/` + `docs/design/` |
| **M — приложение** | SPA, небольшое приложение, сайт на фреймворке | Средний: `_dev/`, `architecture/`, `design/`, при нужде `api/` |
| **L — продукт** | Fullstack-продукт, много сервисов/страниц, БД, тарифы | Полный набор (все папки) |

Дефолт, если пользователь сказал «бери дефолты» или «реши сам»: **профиль S**, стек —
универсальная статика (HTML/CSS/JS), память развернуть. От малого к большому масштабировать
легко; раздутый каркас на пустом месте — мусор.

## Шаг 2 — Настройки Claude Code (`.claude/`)

Создай папку `.claude/` и два файла настроек (по официальной схеме Claude Code).

> Это **личные настройки Андрея** — его рабочий пресет. Если передаёшь установщик
> другому человеку, предупреди, что тут его дефолты, и пусть подгоняет под себя.

### `.claude/settings.json` — проектные (коммитятся в репо)
```json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(git status:*)",
      "Bash(git diff:*)",
      "Bash(git log:*)",
      "Bash(git add:*)",
      "Bash(git commit:*)",
      "Bash(git branch:*)",
      "Bash(git checkout:*)",
      "Bash(git push:*)",
      "Bash(git pull:*)",
      "Bash(git tag:*)",
      "Bash(npm run:*)",
      "Bash(npx:*)",
      "Bash(ls:*)",
      "Bash(cat:*)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)"
    ],
    "ask": []
  },
  "env": {
    "ENABLE_TOOL_SEARCH": "true"
  },
  "showThinkingSummaries": false,
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup",
        "hooks": [
          {
            "type": "command",
            "command": "node",
            "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/load-handoff.mjs"]
          }
        ]
      }
    ]
  }
}
```
Расширяй `allow` под стек проекта: Docker — `Bash(docker-compose:*)`, `Bash(docker ps:*)`;
Python — `Bash(python3:*)`, `Bash(pytest:*)`.

**SessionStart-хук** детерминированно подаёт cold-start в каждую новую сессию (надёжнее, чем
надеяться, что модель прочтёт память). Хук записан в exec-форме (`command` + `args`): Claude Code
запускает node напрямую, без оболочки, поэтому он одинаково работает на macOS и на Windows.
Создай скрипт `.claude/hooks/load-handoff.mjs`:
```js
#!/usr/bin/env node
// Подаёт последний handoff из прошлой сессии в контекст новой — cold-start.
import { readFileSync } from "node:fs";
import path from "node:path";

const projectDir = process.env.CLAUDE_PROJECT_DIR ?? process.cwd();
try {
  const handoff = readFileSync(path.join(projectDir, ".claude", "HANDOFF.md"), "utf8");
  if (handoff.trim() !== "") {
    process.stdout.write(
      `=== COLD START — handoff из прошлой сессии (продолжай отсюда) ===\n${handoff}\n=== /COLD START ===\n`,
    );
  }
} catch {
  // Файла нет — тишина.
}
```
`HANDOFF.md` пишется в конце сессии (см. Шаг 5, завершение сессии). Если файла ещё нет —
хук молчит. `${CLAUDE_PROJECT_DIR}` Claude Code подставляет сам.

### `.claude/settings.local.json` — личные (в `.gitignore`)
```json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [],
    "deny": [],
    "ask": [],
    "defaultMode": "bypassPermissions"
  },
  "outputStyle": "default"
}
```

## Шаг 3 — Каркас `docs/` (по профилю из Шага 0)

**Создавай только папки нужного профиля.** Лишние пустые папки = мусор. От малого к
большому всегда можно дорастить позже (новый раздел = новая папка + строка-ссылка в `CLAUDE.md`).

**Профиль S (простой):** минимум. Либо один файл `docs/README.md` (что за проект, скоуп,
что сделано), либо две папки:
```
docs/
├── _dev/         # скоуп + простой чеклист задач
└── design/       # если есть дизайн/референсы (для лендинга обычно да)
```

**Профиль M (приложение):** ядро разработки + архитектура:
```
docs/
├── _dev/             # черновик скоупа + мастер-трекер
│   └── sub-trackers/ # субтрекеры по фазам/модулям
├── architecture/     # overview, ADR, stack
├── design/           # UI/UX, палитры, wireframes
└── api/              # внешние интеграции (если есть)
```

**Профиль L (продукт):** полный набор:
```
docs/
├── _dev/                    # черновик скоупа + мастер-трекер
│   └── sub-trackers/        # субтрекеры по фазам/модулям
├── services/                # спека каждого сервиса/страницы (одна папка = один сервис)
├── pricing/                 # тарифы, монетизация
├── architecture/            # overview, ADR, phases, stack
├── database/                # схема БД, миграции
├── api/                     # внешние интеграции, email
├── infra/                   # деплой, сервера
└── design/                  # UI/UX, палитры, wireframes
```

В каждую созданную папку — `README.md` на 1–2 строки (что сюда кладём). Контентом НЕ наполняй —
это следующий этап (бриф → доки). Для профиля S детальная спека вообще может не понадобиться.

## Шаг 4 — `.claude/CLAUDE.md` (инструкции для агента, по Anthropic)

Сгенерь `.claude/CLAUDE.md` — это **инструкции для агента**, НЕ оглавление-таблица.
Официальные правила Anthropic: концентрированно и конкретно, **до 200 строк**, на **английском**
(это контекст для агента, как код и коммиты). Содержимое: commands, architecture, conventions,
git workflow. На детальную доку в `docs/` ссылайся **по пути в тексте** (не через `@import` —
импорт грузит файлы целиком в контекст при старте и раздувает токены).

Шаблон ниже — **адаптируй под проект**: перечисляй только реально созданные папки `docs/`,
выбрасывай неприменимые строки (у статики нет Test/Lint — убери; у простого проекта нет i18n —
убери). Лучше короткий точный файл, чем шаблон с мёртвыми пунктами.

```markdown
# <Project Name>

<one line: what this project is and who it's for>

## Commands
<!-- fill in once tooling exists; drop lines that don't apply -->
- Install: `<cmd>`
- Dev / serve: `<cmd>`
- Test: `<cmd>`
- Lint / format: `<cmd>`

## Architecture
- Stack: <stack>
- Detailed specs live under `docs/` — read on demand. <!-- list ONLY folders you created -->
  e.g. `docs/architecture/`, `docs/design/`, `docs/services/<name>/`.

## Conventions
- Code, identifiers, comments, commit messages: English.
- Discussion and `docs/`: Russian. <!-- UI strings via i18n — only if the project is localized -->
- Modular files, no monoliths. Keep code clean and safe; don't over-engineer.

## Git workflow
- Commit to `develop`; `main` is release-only.
- Conventional Commits (`feat:` / `fix:` / `docs:` / …). Push only with explicit approval.

## Working method
Architect–implementer: the user designs and specifies, Claude Code implements.
One session = one atomic task.
```

Размещение: `.claude/CLAUDE.md` (официально равнозначно `./CLAUDE.md`, корень чище).

## Шаг 5 — Память проекта и cold-start (САМЫЙ ВАЖНЫЙ шаг)

> **Это ядро всего метода.** Цель: каждую новую сессию начинать с готового cold-start
> контекста из прошлых — без перечитывания всего. `work-protocol` обязателен ВСЕГДА,
> даже для простейшего проекта профиля S. Без него установка не считается завершённой.

Память — официальная **Auto memory**: `~/.claude/projects/<project>/memory/`, где `<project>`
берётся из git-репо (вне git — из корня проекта). `MEMORY.md` — индекс (грузится в каждую
сессию, первые 200 строк / 25KB); протоколы — отдельными topic-файлами. Создай файлы +
строки-указатели в `MEMORY.md` (формат frontmatter — см. глобальный `~/.claude/CLAUDE.md`).

Cold-start стоит на двух опорах (по best practices «two-file system»):
1. **Память** (`MEMORY.md` + протоколы) — постоянные правила и контекст проекта.
2. **`.claude/HANDOFF.md`** — нарратив «где встали», пишется в конце сессии, а в начале
   следующей его детерминированно подаёт **SessionStart-хук** (Шаг 2). Это «железобетон»:
   не надеемся, что модель прочтёт память, — хук впрыскивает handoff сам.

### Протоколы, которые сеет установщик

**`work-protocol`** (type: feedback) — главный, создаётся всегда. Возьми текст ниже целиком
(он универсальный, не привязан к стеку):

```markdown
---
name: work-protocol
description: Протокол работы — сессии, git, язык, автономия, стандарты кода, старт/завершение
metadata:
  type: feedback
---

## Сессии
- Одна сессия = одна атомарная задача.
- Старт: есть handoff (его подаёт SessionStart-хук) → идти по нему, читать только указанные
  точки входа. Нет → `MEMORY.md` + актуальный трекер/скоуп, без веерного чтения всей памяти.
- Держать контекст лёгким (~60% окна) — лучше свежая сессия, чем раздутая.

## Git и коммиты
- Коммитим в `develop`; `main` — только релизы (develop → main).
- Conventional Commits (feat/fix/docs/refactor/chore…), на английском.
- Чекпоинт-коммиты по ходу, на каждом завершённом куске — не свалкой в конце.
- Пуш — только с явного разрешения (исключение: протокол завершения сессии — там пуш штатный).

## Завершение сессии («Завершаем сессию»)
1. Тесты (если есть). 2. Закрыть вопросы сессии. 3. Открытые вопросы — кратко в память.
4. Записать handoff в `.claude/HANDOFF.md` (перезаписать) — его подхватит SessionStart-хук
   в начале следующей сессии. **В чат handoff НЕ выводить** (решение 2026-07-25: файла
   достаточно, ручное копирование блока из чата отменено). Компактно, карта на экран:
   где встали (задача + статус) · сделано (2-4 пункта) · следующий шаг (первое конкретное
   действие) · точки входа (2-3 ссылки на файлы/спеки/память) · открытые нюансы.
5. Коммит + **пуш** — в протоколе завершения оба штатные шаги, отдельного разрешения не
   ждать (вне протокола завершения пуш по-прежнему только с явного разрешения).

## Автономия решений
- Реализацию (КАК построено: структура кода, паттерны, слои, зависимости, инфра/сеть, схема
  данных, нейминг, рефакторинг) Claude ведёт сам по best practices — в одну строку поясняя
  выбор, без развилочных вопросов.
- Андрею выносить ТОЛЬКО: (1) критичное/необратимое с ценой (деньги, прод-данные, безопасность,
  смена продуктовой стратегии); (2) UI — когда есть готовый визуал; (3) функционал — что фича
  даёт пользователю. Развилку реализации через AskUserQuestion НЕ выносить.

## Язык
- Код (имена, комментарии, коммиты) — английский.
- Общение и `docs/` — русский. UI-строки — через i18n (если проект локализуется).

## Стандарты кода
- Чисто и безопасно; никаких монолитов — дробить на модули.
- Оставлять подсказки будущему себе в коде, держать актуальными.
- Не усложнять: варианты взвесить внутри себя, выбрать лучший сам.
- Смотреть на решение под разными углами.

## Инструменты и знания
- Доку библиотек — всегда через Context7 (MCP), не из памяти (веса устаревают).
- Устаревшие знания (текущий год) — веб-поиск + доки Anthropic.
- Отладка в браузере — через Claude in Chrome.

## Память
- Держать в порядке, без мусора; выполненное удалять (история в коммитах).
- Всегда актуальный cold-start: по слову «продолжаем» ясно, с чего начать.

## Разработка
- Перед новой страницей/сервисом — проверить доку и план. Нет → сначала планируем.
- Локально до завершения; сервер — перед деплоем.
```

Остальные протоколы — по необходимости (профиль/наличие данных):
- **`product-vision`** (type: project) — что строим и зачем (из брифа, Шаг 0). Создавать всегда.
- **`docs-protocol`** (type: project) — какой профиль развёрнут и структура `docs/`; правило
  «`.claude/CLAUDE.md` — инструкции для агента, детальная дока в `docs/`». Профиль M/L.
- **`stage-scope`** (type: project) — скоуп текущего этапа. Заполнить, когда появится план.

Создай также **пустой `.claude/HANDOFF.md`** с заглушкой («Первая сессия — handoff появится
после `Завершаем сессию`»), чтобы хук не молчал и структура была на месте.

Правила памяти: без мусора, выполненное — удалять (история в коммитах), всегда актуальный cold-start.

## Шаг 6 — Убрать за собой и отдать проект

1. Скопируй обе методички в доки проекта как референс — **копируй (`cp`), не переноси и не удаляй**.
   Установщик может лежать в отдельной шаблонной папке (а не внутри проекта); он переносимый и
   должен остаться целым для следующих проектов.
   - `PROJECT-BOOTSTRAP.md` → `docs/architecture/PROJECT-BOOTSTRAP.md`
   - `INSTALL.md` → `docs/architecture/INSTALL.md`
2. Покажи пользователю короткий итог: что создано + следующий шаг.

**Следующий шаг (подсказать пользователю, не делать самому):**
- `git init` + ветки `main`/`develop` — когда пользователь готов (см. методичку, шаг 1).
- Профиль M/L: прогнать бриф через **`fullstack-architect`** → PRD → ARCHITECTURE → PLANNING →
  TASKS, разложить по `docs/`. Профиль S: обычно не нужно — сразу к коду, доку ведём по факту.
- Подключить свои скиллы и MCP (CodeGraph, Context7 и т.д.) — на усмотрение пользователя,
  установщик скиллы намеренно не тащит (у каждого свой набор под свои задачи).

## ⚠️ Правила установщика

- **Идемпотентность:** перед созданием файла проверь, не существует ли он. Существует — спроси,
  перезаписать или пропустить. Не затирай молча.
- **Если папка уже git-репо или непустой проект** — не делай `git init`, не трогай чужие файлы,
  предупреди пользователя и спроси, что разворачивать.
- **Ничего не пушим, ничего не удаляем из данных пользователя** без явного разрешения.
- Удаление — только через `trash`.
