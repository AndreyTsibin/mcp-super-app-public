# Плейбук архитектуры знаний для проекта с Claude Code

> **Что это.** Переносимый свод правил: как устроить документацию, память и протоколы так,
> чтобы работа с Claude Code не деградировала по мере роста проекта. Файл самодостаточен —
> положи его в новый проект, попроси Claude прочитать и исполнить чек-лист внедрения (§10).
> **Версия:** v1.0 (2026-08-29) · выведен из практик Anthropic и полного внедрения на живом
> проекте среднего размера. Каждое правило здесь применено и измерено: cold start 9 178 → 6 859
> токенов, «мастер-трекер + субтрекер» 18 483 → 3 917, память 45 файлов → 19, документов-сирот
> 7 → 0, протухших путей к коду 35 → 0.

## 1. Модель проблемы

Документация и память растут линейно с проектом. Контекст — нет. Всё, что Claude читает
«на всякий случай», отнимает место у того, что он должен понять по задаче, и **прямо роняет
качество работы**.

Считать нужно **два разных бюджета**, и второй обычно дороже:

| Бюджет | Что это | Типичная ошибка |
|--------|---------|-----------------|
| **Cold start** | Грузится КАЖДУЮ сессию до первой строки задачи: `CLAUDE.md` (глобальный + проектный), индекс памяти, впрыск SessionStart-хука | Оптимизируют только его — он на виду |
| **Вторая волна** | Что сессия читает, чтобы понять, ЧТО делать: трекер, субтрекер, спека подсистемы | Не считают вообще. На живом проекте вышла **вдвое дороже** cold start ✅ |

**Правило приоритета:** сначала мерь вторую волну. Раздутый трекер задач съедает больше, чем
весь `CLAUDE.md`, и платится он на каждой сессии по той же фиче.

## 2. Слои знания

Каждый файл отвечает на один вопрос и имеет свой срок жизни. Если не отвечает — он мусор.

| Слой | Отвечает на вопрос | Когда читается | Когда умирает |
|------|--------------------|----------------|---------------|
| `.claude/CLAUDE.md` | Как работать с ЭТИМ репозиторием (стек, команды, конвенции, протоколы) | Всегда (cold start) | Живёт всегда, но не растёт: детали уезжают в слои ниже |
| `.claude/rules/*.md` (`paths:`) | Правила для конкретной части кода | Только при работе с совпавшими файлами | Вместе с частью кода |
| `HANDOFF.md` | Где встали, что дальше, что читать | Всегда (SessionStart-хук) | Перезаписывается каждую сессию |
| Трекер / субтрекер | Что делаем и в каком порядке | При заходе в фичу | Задача закрыта → строка статуса; фаза закрыта → трекер сворачивается |
| Спека сервиса | Как система устроена сейчас | При работе с подсистемой | Переписывается при изменении, не дополняется слоями |
| Журнал решений | Что выяснили на практике, чтобы не наступать повторно | По grep, перед заходом в подсистему | Почти никогда (это и есть накопленный капитал) |
| Память | Указатели и правила работы; то, что нельзя вывести из репозитория | Индекс — всегда, файлы — по требованию | Факт устарел / переехал в репозиторий |

**Ключевое разделение, из которого следует всё остальное:**

- **Операционный лог** (сделал X, N тестов, коммит, список файлов) — умирает вместе с задачей.
  Его помнит git. В документации он второй слой правды, который устаревает независимо.
- **Durable-знание** (почему решено так, найденная ловушка, замеренная цена, грабли
  эксплуатации) — переезжает в журнал решений или спеку. **Этого в git не ищут.**

## 3. Правило маршрутизации: куда писать

Дерево решений при вопросе «куда это записать»:

```
Выводится из кода или git-истории?
├── ДА  → не записывать вообще (статусы, списки файлов, структура модулей, «что было сделано»)
└── НЕТ → Это про КОНКРЕТНУЮ подсистему?
          ├── ДА  → Как устроено сейчас?      → спека сервиса
          │         Почему так / какие грабли? → журнал решений
          │         Правило для файлов по маске? → .claude/rules/
          └── НЕТ → Про то, КАК со мной работать? → CLAUDE.md (протокол) или память (feedback)
                    Про текущий план?              → трекер
                    Где встали прямо сейчас?       → HANDOFF.md
```

**Тест на запись в память:** если факт можно получить, прочитав репозиторий, — он не идёт
в память. Память для того, что живёт только в голове человека: решения, предпочтения,
приоритеты, внешние ссылки, договорённости о процессе.

## 4. Бюджеты

Цифры — рекомендации Anthropic (docs.claude.com) плюс наши замеры. Мерить обязательно: без
числа «раздуто» — вопрос вкуса.

**Бюджет ставится в токенах, не в строках** ✅. Замер по 55 документам одного проекта: плотность
гуляет от **16 до 109 токенов на строку** — в семь раз. Файл без переносов (одна мысль = одна
строка на 2 700 символов) при «всего 138 строках» весит 15k токенов, а мастер-трекер на 96
строках — 4.5k. Строчный лимит такие файлы пропускает: они выглядят компактными и стоят как
пятикратно бо́льшие. Строки годятся как грубый ориентир только при hard-wrap ~100 символов
(тогда медиана ≈20 т/стр); проверять — токенами.

| Что | Бюджет | Жёсткость |
|-----|--------|-----------|
| Весь cold start (system + `CLAUDE.md` + память + впрыск) | **≤15–20k токенов** | рекомендация |
| `CLAUDE.md` | **≤4k токенов** (≈200 строк) | рекомендация |
| Любой файл памяти / `CLAUDE.md` | **≤40 000 символов** | предупреждение CLI «large file will impact performance»; при >4 MiB файл вообще не грузится |
| Индекс памяти | одна строка на запись | сверх лимита индекс **усекается** — часть записей просто исчезает из виду |
| Впрыск SessionStart-хука | **≤5k токенов** | рекомендация |
| Трекер фичи | **≤4k токенов** — план, не архив | наше правило ✅ |
| Спека / документ | **≤8k токенов**, иначе делить или давать шапку-индекс | наше правило ✅ |

**Ориентир из живого проекта** ✅ (средний размер, ~15 фич, ~26k строк кода): cold start
9.2k токенов при 55 документах и 45 файлах памяти — это **норма**. А один субтрекер закрытой
фазы дорос до 15k токенов — вот это патология: он один стоит дороже, чем весь старт сессии.

## 5. Механика Claude Code: чем что решать

| Механизм | Когда грузится | Для чего использовать |
|----------|----------------|------------------------|
| `.claude/CLAUDE.md` (или корневой `CLAUDE.md`) | Всегда | Только то, что нужно в ЛЮБОЙ сессии: стек, команды, конвенции, протоколы, карта документации |
| Вложенный `CLAUDE.md` (`frontend/`, `backend/`…) | При работе внутри этой директории | Крупная специфика подпроекта, если он самостоятелен |
| **`.claude/rules/*.md` с `paths:` во frontmatter** | Только когда файловый инструмент трогает совпавший файл ✅ (см. ниже) | **Рычаг разгрузки.** Ловушки фреймворка, конвенции слоя, правила тестирования — по маске `frontend/**`, `backend/**` |
| Skills (`.claude/skills/`) | Описание — всегда, тело — на вызов | Многошаговые ПРОЦЕДУРЫ: завершение сессии, заведение сущности по рецепту, релиз |
| Память | Индекс — всегда, файлы — по требованию | Указатели, правила работы, решения человека |
| SessionStart-хук | Всегда | Ровно «где встали» — handoff, и ничего больше |
| Субагент | По вызову, в своём контексте | Объёмный поиск и чтение: в основной контекст приходит вывод, а не файлы |

**Где держать `CLAUDE.md`** ✅ (проверено на Claude Code 2.1.238 грепом по бинарю CLI):
корневой `./CLAUDE.md` и `./.claude/CLAUDE.md` — **равноправны, оба грузятся всегда**.
Предпочтительнее второй: всё хозяйство агента (`CLAUDE.md`, `rules/`, `skills/`, `hooks/`,
`settings.json`, `commands/`, `agents/`) лежит в одной папке, корень репозитория чистый.
Единственная плата — относительные ссылки внутри файла становятся `../docs/…`; переписать
разом при переносе. Вложенные `CLAUDE.md` в подпроектах (`frontend/CLAUDE.md`) при этом
работают как раньше — грузятся, когда работа идёт внутри их директории.

### Как на самом деле работают `.claude/rules/` ✅

Проверено экспериментом с правилами-зондами на Claude Code 2.1.238 (и сверено с кодом CLI).
Механика важнее, чем кажется из документации: **у неё узкий триггер, и на нём легко построить
правило, которое молчит именно тогда, когда нужно.**

| Вопрос | Ответ |
|--------|-------|
| Что делает `paths:` во frontmatter | Переводит правило в **условный** режим. Без `paths:` правило грузится ВСЕГДА, как `CLAUDE.md` — это второй, редко замечаемый способ применения каталога |
| `paths: ["**"]` | Тоже даёт безусловное правило (маска схлопывается) — не способ «включить везде дёшево» |
| Что именно триггерит подгрузку | **Чтение файла инструментом Read**; плюс `@`-упоминание файла в промпте и открытие файла в IDE |
| Что НЕ триггерит | **Правка через Edit/Write** и **чтение через шелл** (`cat`, `sed`, `grep`). Файл меняется — правило молчит |
| Как матчится маска | Семантика `.gitignore` по пути относительно корня проекта. `frontend/**` эквивалентно `frontend` и покрывает всё поддерево; `*.css` сработает на любом уровне |
| Когда подхватывается новый файл правила | Сразу, **без перезапуска сессии** (в отличие от скиллов и хуков) |
| Сколько раз приезжает | Один раз за сессию на файл правила — дальше он уже в контексте |
| Вложенность | Подпапки внутри `.claude/rules/` обходятся рекурсивно |

**Следствие, определяющее состав правил.** Триггер — чтение, а не правка. Значит в
`.claude/rules/` кладут знание, которое нужно **тому, кто открыл файл**: ловушки этого слоя,
локальные конвенции, «сначала посмотри вот сюда». Знание, нужное до чтения файлов (архитектура,
команды, протоколы), там бесполезно — сессия дойдёт до него уже после того, как приняла решение.
А в окружении, где агент работает преимущественно шеллом, правила не сработают вовсе — это
проверяется одним зондом за минуту и решает, стоит ли вообще городить каталог.

**Проверка зондом (минута работы, снимает все догадки):** положить в `.claude/rules/probe.md`
frontmatter `paths: ["<маска>"]` и уникальный маркер в теле → прочитать файл под маской → прочитать
файл вне её. Маркер обязан появиться ровно в первом случае. Тем же приёмом проверяется любая
гипотеза о загрузке контекста: **зонд с маркером дешевле, чем чтение документации о том, как оно
должно работать.**

**Чего НЕ делать:**

- **`@path`-импорты в `CLAUDE.md`** — раскрываются на старте целиком. Организуют текст, но
  контекст не экономят. Разгрузка — это `rules`, а не импорты.
- **Класть в `CLAUDE.md` справочный материал и примеры** — он читается всегда, а нужен раз.
- **Дублировать статусы задач в память** — они устаревают в тот же день и создают вторую
  правду. Трекер — единственный источник статуса.

## 6. Протоколы

### Старт сессии
Хук впрыскивает `HANDOFF.md` → идти по нему, читать **только** названные точки входа.
Веерное чтение памяти и документации — запрещено: если нужного нет в handoff, значит нужен grep,
а не чтение целиком.

### Завершение сессии
1. Прогнать тесты (если код менялся).
2. Durable находки сессии → журнал решений / спека. Операционный лог — никуда, он в git.
3. Обновить трекер: статус задачи, а не пересказ сделанного.
4. **Перезаписать `HANDOFF.md`**: где встали · сделано (2–4 пункта) · следующий шаг (первое
   конкретное действие) · точки входа (2–3 файла, точечно) · открытые нюансы. Один экран.
5. Коммит (+ пуш, если это штатная часть протокола).

### Закрытие фазы
Отдельным проходом, не «по ходу»:
1. Закрытые задачи вычистить из трекера — их описания и итоги уже в git. Закрытая фаза =
   одна строка статуса.
2. Durable перенести в журнал решений / спеку. Правило: **«durable перенеси, лог выкинь»**.
3. Консолидировать память: слить дубли, снять устаревшее, подрезать индекс.
4. Перемерить cold start и вторую волну — цифрой подтвердить, что стало дешевле.

## 7. Стражи (иначе всё вернётся)

Правила без автоматики держатся ровно до первого аврала.

| Страж | Что ловит | Почему обязателен |
|-------|-----------|-------------------|
| **Битые markdown-ссылки** | `[текст](путь)` в никуда | Дёшево, ловится 100 % |
| **Пути к коду в бэктиках** | `` `apps/foo/bar.py` `` после рефакторинга | ✅ На живом проекте markdown-ссылки были целы **все** (0 из 444), а путей в бэктиках гнило **35** — включая указатель в самом `CLAUDE.md`. Никто их не проверяет — они и гниют |
| **Раздувание** | Трекер / индекс памяти вышли за бюджет (мерить в токенах, см. §4) | Раздутый индекс памяти усекается молча — запись остаётся на диске, но перестаёт существовать для сессии |
| **Замер контекста** | Cold start в токенах | Без числа «до/после» перестройка недоказуема |

Страж ссылок обязан **исключать примеры синтаксиса** — и в блоках кода, и в инлайн-бэктиках
(`[текст](путь)` в таблице тоже ложное срабатывание) — и корректно переваривать скобки в путях
(`app/(public)/layout.tsx`). Иначе он даёт ложный шум и его перестают читать. ✅ Проверено дважды:
оба раза все «битые» ссылки оказались этими двумя случаями, реальных — ноль.

**Проверять стражей поломкой, а не наличием:** подсунуть каждому битую ссылку / раздутый файл
и убедиться, что он упал. Страж, который никогда не падал, обычно не работает.

Скрипт замера (положить в репозиторий, чтобы замер был воспроизводим):

```python
# tools/context_cost.py — python tools/context_cost.py CLAUDE.md MEMORY.md HANDOFF.md
import sys, tiktoken
enc = tiktoken.get_encoding("o200k_base")   # приближение ±10% к токенизатору Claude
total = 0
for p in sys.argv[1:]:
    n = len(enc.encode(open(p, encoding="utf-8").read()))
    total += n
    print(f"{n:>7} tok  {p}")
print(f"{total:>7} ИТОГО")
```

В интерактивном терминале то же показывают `/context` (что занимает контекст) и `/usage`
(токены и стоимость сессии) — если они доступны, начинать с них.

## 8. Антипаттерны (все встречены живьём ✅)

1. **Память ведёт второй трекер.** Запись на 185 строк с итогами закрытых задач, номерами
   коммитов и счётчиками тестов — полный дубль трекера и git. Durable в ней было на 4 абзаца.
2. **Файл, который сам признаёт дублирование.** Начинается со слов «статусы сюда не дублирую,
   истина — в трекере» и следом перечисляет статусы всех фич.
3. **Индекс пересказывает вместо навигации.** Строка индекса на 250 символов с выжимкой
   содержимого = второй слой правды, устаревающий независимо от файла. В индексе должно быть
   имя + одна фраза «когда это читать».
4. **Навигация обрывается на папке.** Карта документации ссылается на каталоги, а не на файлы →
   документы-сироты, которые можно найти только зная, что они есть.
5. **Архив лежит среди живого.** Спека снесённой подсистемы в одной папке с рабочими — читается
   как актуальная, пока не дойдёшь до шапки.
6. **Трекер как архив итогов.** 633 строки, из них 85 % — разбор закрытых задач; чтобы прочитать
   30 строк плана, сессия платит 14k токенов.
7. **Правило чистки без момента срабатывания.** «Прибираться после фазы» помнится ровно до
   следующей фазы. Нужна привязка к событию + страж.

## 9. Что сознательно НЕ делаем

- **Не оптимизируем cold start первым.** Он на виду, но дешевле второй волны.
- **Не пишем детальные спеки на отложенное.** Глубина детализации убывает с удалением фичи;
  детализируем перед заходом. Спека на то, что ещё поменяется, — выкинутый труд.
- **Не заводим абстракций под один случай** — ни в коде, ни в документации. Второй проект —
  повод обобщить, «а вдруг понадобится» — нет.

## 10. Чек-лист внедрения в новом проекте

1. **Замерить исходное состояние** — cold start и вторую волну в токенах. Без числа «раздуто»
   остаётся вопросом вкуса, а «стало лучше» — недоказуемым.
2. `.claude/CLAUDE.md` — стек, команды, конвенции, карта документации, протоколы. **≤4k токенов.**
   Всё, что специфично для части кода, — не сюда. Класть сразу в `.claude/`, чтобы хозяйство
   агента было в одной папке (ссылки на доки станут `../docs/…`).
3. **Проверить зондом**, работают ли `.claude/rules/` в вашем режиме работы (§5), и только потом
   решать, заводить ли каталог. Триггер узкий — правило легко получить молчащим.
4. `docs/` — плоско и по назначению: `architecture/` (как устроено + ADR), `services/<name>/`
   (спеки), `decisions/` (журнал решений), `_dev/` (трекеры + `HANDOFF.md`).
5. Журнал решений завести **сразу пустым** с фиксированным форматом (иначе grep не работает):
   `### <ID> · суть` + строка тегов + **Грабли → Решение → Не делать** + дата. ID = префикс файла
   плюс номер внутри файла — так не нужно помнить сквозную нумерацию. **Индекс журнала не
   перечисляет записи** (оглавление берётся `grep -rn "^### "`), иначе это второй слой правды.
6. **Поставить триггер чтения журнала в `CLAUDE.md`** — без него файл наполняется, но не читается.
7. SessionStart-хук: впрыскивает `HANDOFF.md`, если он непустой, и молчит иначе.
8. Память: индекс — одна строка на запись, тело в файлах; критерий записи — **«нельзя вывести из
   репозитория»**. Всё техническое живёт в `docs/`, память хранит решения человека, правила
   работы и доступы.
9. Стражи из §7 — в тот же гейт, что и тесты, и **каждому подсунуть поломку**.
10. Раз в фазу — протокол закрытия фазы (§6) и повторный замер.

**Порядок важен:** сначала замер (1), потом чистка второй волны — трекеры (§4), и только потом
всё остальное. Оптимизация cold start, с которой хочется начать, обычно даёт меньше всего.

## 11. Чему научил первый прогон

- **Автоматический страж даёт ложные срабатывания там, где документ говорит о механизме, а не о
  файле** (описание чужого инструмента, плановый путь, цитата битой ссылки в отчёте аудита).
  Держите короткий явный список исключений **с объяснением на каждое** — исключение без причины
  через полгода неотличимо от бага. Отчёты-аудиты проще исключать целиком: цитировать
  протухшие пути — их работа.
- **Проверка путей ловит расхождение доков с кодом лучше, чем ревью.** Все 35 протухших путей
  прошли через десятки сессий, и ни одна их не заметила.
- **Самая дорогая ложь живёт в файле, который читают чаще всего.** В нашем случае `CLAUDE.md`
  описывал модель расписания, снесённую двумя фазами раньше.
- **Правило чистки применяйте и к трекеру самой перестройки.** Он тоже успевает стать архивом.
