# Решения: сам MCP-сервер

Схемы и описания тулов, MCP-instructions, самопроверки старта, эвалы.
Формат и правила — `README.md`.

### SRV-1 · Меню точек входа живёт в MCP-instructions сервера
`instructions` `ux`
**Грабли:** правило «спроси `AskUserQuestion` с тремя опциями» лежало только в личном
`~/.claude/CLAUDE.md` Андрея. У коллег на публичной копии не было ни меню, ни намёка, что оно
задумано — восемь голых имён тулов.
**Решение:** правило переехало в `instructions` сервера (`src/index.ts`) и едет вместе с ним,
попадая в системный контекст при каждом старте. Там же — вендоренные скиллы по назначению,
чтобы агент открывал каталог `install_skill`, а не гадал. Цена ~450 токенов на сессию.
**Не делать:** не описывать поведение сервера в личных настройках одного человека — для всех
остальных этого поведения не существует.

### SRV-2 · Каталог скиллов лежит в описании параметра, а не в read-only туле
`schema` `evals`
**Грабли:** сняли `list_skills` — и агент перестал видеть, что скиллы делают: в схеме остался
голый enum из шести id. По брифу «поставь скилл для анимаций» выбрать было не из чего.
**Решение:** описание параметра `skill` генерится из реестра `SKILLS` (id, тип, назначение,
команда установки для proxied). Источник правды один, дрейфовать нечему. Эвалы подтвердили:
модель ответила по этому описанию на шесть вопросов, не вызвав ни одного тула.
**Не делать:** не добавлять read-only тул ради «спросить, что будет сделано», если ответ уже
целиком лежит в схеме — это вторая сущность с тем же содержимым (предложение модели в
`<feedback>` эвалов, отклонено).
_2026-08-17_

### SRV-3 · Схема и описание собираются в момент регистрации тула, не при импорте
`env` `schema`
**Грабли:** `.env` грузится в `index.ts` **после** того, как отработали все `import`. Константа
уровня модуля, читающая `process.env`, видит пустоту — гейт Magnific по наличию ключа не
работал бы никогда.
**Решение:** `buildInputSchema` / `buildOutputSchema` / `buildDescription` вызываются внутри
`registerCreateImage`.
_2026-08-17_

### SRV-4 · Провайдер без ключа не существует для установки
`schema` `magnific`
**Решение:** нет `MAGNIFIC_API_KEY` — у `create_image` нет ни параметра `provider`, ни объекта
`magnific`, в описании ни слова про Mystic (1950 символов против 2689), строка в instructions
сжимается до «генерация через OpenRouter». Провайдер, на котором установка физически не может
генерировать, не оплачивается токенами описания. Это же делает исходники двух копий репозитория
идентичными — вычищать Magnific при порте не нужно.
_2026-08-17_

### SRV-5 · Отставание от origin проверяется git-протоколом, а не GitHub API
`self-check` `private-repo`
**Грабли:** проверка обновлений через `/compare` GitHub API. **Приватный репозиторий без токена
отдаёт 404** — у Андрея баннер не появился бы никогда.
**Решение:** `git ls-remote origin <ветка>`: те же креды, что у клона, ноль rate limit, любой
хостинг. Точное отставание считается, когда remote-коммит уже есть локально; свой незапушенный
HEAD распознаётся и молчит.
_2026-08-17_

### SRV-6 · Кэш самопроверки — в `os.tmpdir()`, не рядом с сервером
`self-check` `update_server`
**Грабли:** кэш лежал в каталоге сервера и появлялся как untracked-файл. `update_server`
отказывался работать на грязном дереве — из-за файла, который сам же сервер и создал.
**Решение:** кэш в `os.tmpdir()` (ключ — хэш пути клона), dirty-проверка смотрит только
отслеживаемые файлы.
_2026-08-17_

### SRV-7 · Обязательность ключа объявляется в `.env.example`, не списком в коде
`env` `self-check`
**Решение:** ключ обязателен ПО УМОЛЧАНИЮ, необязательный помечается строкой `# optional` над
ним. Список обязательных ключей в коде отвергнут: добавить ключ в образец и забыть про
константу — ровно тот промах, который проверка и должна ловить. Дефолт «обязателен» ошибается
в сторону «заметить». Ключ из `process.env` считается заданным: экспорт из шелла или конфига
MCP-клиента работает не хуже строки в файле.
_2026-08-17_

### SRV-8 · Правка без `npm run build` и рестарта не применяется
`эксплуатация`
Главная грабля разработки: сервер — запущенный процесс, симптом выглядит как «фикс не
сработал». Ловится самопроверкой старта (mtime свежайшего файла в `src/` против `dist/index.js`);
под `npm run dev` проверка пропускается.
_2026-08-17_

### SRV-9 · Эвалам не нужен ключ Anthropic
`evals`
Харнесс ходит через Anthropic SDK, а тот слушается переменных окружения; у OpenRouter есть
совместимый `/v1/messages` — годится ключ из `.env` сервера. Команда прогона — в шапке
`docs/_dev/evaluation.xml`. В venv ставить `mcp<2`: в 2.0 `streamablehttp_client` переименован
в `streamable_http_client`, и `connections.py` падает на импорте, хотя нам хватило бы stdio.
_2026-08-17_

### SRV-10 · Харнесс эвалов сверяет ответы строгим равенством строк
`evals`
**Грабли:** вопрос «провалился» ложно — модель дала верную команду внутри абзаца пояснений,
а `response_value == answer` этого не прощает.
**Решение:** каждый вопрос обязан требовать голый ответ («ответь числом», «только командой»).
Правило записано в шапку XML.
**Не делать:** не чинить чужой харнесс. Ошибка «TypeError: Object of type TextContent is not
JSON serializable» в отчётах — это `evaluation.py:117` делает `json.dumps` над списком
`TextContent`; прямой вызов тула по stdio отвечает корректно. Просто помнить, читая отчёты.
_2026-08-17_

### SRV-11 · Точку входа предлагает сервер, а не память пользователя
`instructions` `онбординг`
**Грабли:** холодный прогон глазами новичка: человек описал задачу своими словами («хочу,
чтобы заявки с лендингов падали в одно место»), не назвав сервер, — и агент повёл обычный
разговор: лекция про готовые CRM и пять вопросов, из них технические («лендинги на чём?»,
«хостинг есть?»). `bootstrap_project` не предложен вообще. И MCP-instructions, и правило,
которое `INSTALL.md` записывает пользователю в `~/.claude/CLAUDE.md`, описывали только
случай «пользователь сказал "запусти mcp-super-app"» — то есть вход открывался фразой,
которую новичок должен помнить.
**Решение:** в instructions добавлен второй случай — человек описывает новую работу, сервер
не называя: одной фразой предложить точку входа (проект → `bootstrap_project`, сайт →
`create_website`, картинка → `create_image`) и дождаться согласия.
**Не делать:** не звать тул молча по догадке — предложение и согласие, иначе агент начнёт
разворачивать каркас на «а можно вообще такое сделать?».
_2026-09-01_

### SRV-12 · Триггеры скиллов правим руками, `skill-creator` их не измеряет
`скиллы` `описания` `инструменты`
**Грабли:** поставили сторонний `skill-creator` (anthropics/skills) ради оптимизации
`description` — он гоняет 20 запросов в цикле и подбирает формулировку. На нашем каталоге
все прогоны дали `recall=0%`, `rate=0/3` на КАЖДОМ запросе, включая заведомо триггерные.
Причина в харнессе: `scripts/run_eval.py` регистрирует тестируемый скилл как слэш-команду
в `.claude/commands/`, а срабатывание ловит по вызову Skill tool — в текущем Claude Code
команды в `available_skills` не попадают, так что триггер невозможен физически. Корень
проекта он ищет от своего cwd и, запущенный из папки скилла, доходит до `$HOME`: мусорные
`.md` летят в глобальный `~/.claude/commands/` и светятся в живой сессии как скиллы. Цена
ошибки — ~185 вызовов `claude -p` на Opus за четыре минуты, все впустую.
**Решение:** описания скиллов пишем руками. Что реально ломало триггер, видно чтением:
`clean-user-facing-text` был описан под Cursor («Use in Cursor», «installed Cursor Rule»),
хотя ставится в Claude Code; у `frontend-design` было две строки без единого триггерного
слова; `humanizer-ru` и `remove-ai-marks` не размечали границу между собой. В описании
держим: русские формулировки запроса (запросы приходят по-русски), явные «не для этого →
туда» на соседние скиллы, и что именно остаётся нетронутым.
**Не делать:** не запускать `run_loop`/`run_eval` из `skill-creator`, пока апстрим не
переедет с `.claude/commands/` на настоящую регистрацию скилла. Сам `skill-creator` как
руководство по структуре скилла годится — сломано только измерение.
_2026-09-05_
